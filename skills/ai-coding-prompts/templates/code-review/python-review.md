## 审查维度与优先级

### P0 — 安全漏洞（必须修复，阻塞发布）
- **SQL 注入**：检查是否使用 f-string / format / % 拼接 SQL 语句，ORM 调用是否使用了 `raw()` / `extra()` 等不安全方法，是否正确使用参数化查询
- **命令注入**：检查是否使用 `os.system()` / `subprocess.call()` 且参数来自用户输入，是否使用 `shell=True`，是否对输入做了充分的校验和转义
- **反序列化漏洞**：检查是否使用 `pickle.loads()` 加载不可信数据、是否使用 `yaml.load()` 而非 `yaml.safe_load()`、是否使用 `eval()` / `exec()` 处理外部输入
- **路径遍历**：检查文件操作是否拼接用户输入作为路径、是否使用 `os.path.realpath()` 校验路径边界、是否存在符号链接攻击风险
- **敏感信息泄露**：检查是否硬编码了数据库密码/API Key/Secret Key、日志中是否打印了敏感数据、异常信息是否向客户端暴露了堆栈详情
- **SSRF 风险**：检查 `requests.get()` / `urllib` 等请求是否使用了用户可控的 URL，是否做了 URL 白名单校验

### P1 — 逻辑错误、异常处理缺陷、资源泄漏（高优先级）
- **逻辑错误**：条件判断是否正确、边界值是否覆盖、浮点数比较是否使用 `math.isclose()`、列表越界/字典键不存在是否做了防护
- **异常处理缺陷**：是否使用裸 `except:` 捕获所有异常（会吞掉 KeyboardInterrupt）、异常处理范围是否过大（try 块包裹过多逻辑）、是否丢失了异常链（`raise ... from e`）、自定义异常是否继承自 `Exception` 而非 `BaseException`
- **资源泄漏**：文件/网络连接是否使用 `with` 上下文管理器、数据库连接是否在 finally 块中关闭、是否正确使用了连接池、临时文件是否清理
- **并发安全**：多线程场景下共享状态是否加锁、是否使用了线程安全的数据结构、GIL 限制下 CPU 密集型任务是否误用多线程
- **数据一致性**：数据库操作是否在事务中执行、事务边界是否合理、是否存在部分提交导致的数据不一致

### P2 — 性能问题（建议修复）
- **N+1 查询**：ORM 查询是否存在循环内查询数据库、是否使用 `select_related()` / `prefetch_related()` 优化关联查询、是否使用了批量操作替代逐条操作
- **GIL 影响**：CPU 密集型任务是否使用了 `multiprocessing` 而非 `threading`、是否考虑了 `asyncio` 异步方案、是否存在 GIL 竞争导致性能退化
- **内存问题**：是否一次性加载大量数据到内存（应用 `iterator` / `chunk` / `generator` 替代列表）、是否存在循环引用导致 GC 压力、大对象是否及时释放
- **算法复杂度**：是否存在 O(n²) 可优化为 O(n log n) 或 O(n) 的场景、列表查找是否应改用集合/字典、字符串拼接是否使用了 `join()` 替代 `+`
- **缓存策略**：计算密集/IO 密集操作是否使用了缓存（`functools.lru_cache` / Redis）、缓存失效策略是否合理、是否考虑了缓存穿透/雪崩

### P3 — PEP 8 合规、类型注解完整性（建议改进）
- **PEP 8 合规**：缩进是否统一为 4 空格、行宽是否超过 88 字符（Black 标准）、导入是否按标准库/第三方/本地分组且无冗余、命名是否符合 snake_case（函数/变量）和 PascalCase（类）规范
- **类型注解**：函数签名是否添加了参数和返回值类型注解、是否使用 `Optional` / `Union` 明确表达可选类型、是否使用了 `TypedDict` / `dataclass` 替代裸字典、是否配置了 `mypy` strict 模式
- **代码组织**：模块是否职责清晰、是否遵循 `__init__.py` 对外暴露公共 API、是否避免了循环导入、常量是否集中管理
- **Pythonic 风格**：是否使用列表推导/生成器表达式替代 map/filter、是否使用 `enumerate()` 替代手动计数、是否使用 `collections` 模块的高级数据结构、是否善用 `walrus operator`（Python 3.8+）

### P4 — 测试覆盖、文档完善度（长期改进）
- **测试覆盖**：核心逻辑是否有单元测试、是否测试了边界条件和异常路径、是否使用 `pytest` fixture 管理测试数据、是否使用了 `mock` / `patch` 隔离外部依赖、测试是否独立可重复
- **文档完善度**：模块/类/函数是否有 docstring（Google/NumPy/Sphinx 风格统一）、参数和返回值是否在 docstring 中说明、复杂算法是否有注释解释意图、README 是否包含快速上手指南
- **日志规范**：是否使用 `logging` 模块替代 `print()`、日志级别是否合理（DEBUG/INFO/WARNING/ERROR）、是否配置了结构化日志（JSON 格式）、是否避免了敏感信息入日志

## 约束条件

1. **安全优先原则**：P0 级别问题必须在审查结果中醒目标注，任何 P0 问题均视为阻塞发布的硬性障碍，不得降级处理
2. **版本感知原则**：审查和修复建议必须兼容 PYTHON_VERSION 声明的版本，不得推荐该版本不可用的语法特性或标准库；若建议使用新版本特性需明确标注版本要求
3. **框架适配原则**：修复建议须与 FRAMEWORK 匹配，Django/Flask/FastAPI 各有不同最佳实践；若 FRAMEWORK 为 None 则基于纯 Python 标准给出建议
4. **可操作性原则**：每一条问题必须附带具体的修复建议和代码示例，禁止仅指出问题而不给方案
5. **上下文关联原则**：审查必须结合 CODE_CONTEXT 中的业务场景，避免脱离业务上下文给出不切实际的建议
6. **Pythonic 原则**：在同等效果下优先推荐 Pythonic 的写法（如使用 `with` / `contextlib` / `dataclass` / `pathlib` 等），但不以 Pythonic 为由忽视安全和性能问题

## 输出要求

1. 输出完整的 Python 代码审查报告，包含元信息、问题列表、统计摘要、改进总结
2. 每个问题需包含：严重级别（P0-P4）、问题分类、代码行号、问题描述、影响分析、修复建议（含代码示例）
3. 对于 P0 和 P1 级别问题，除给出修复建议外，还需说明如果不修复可能导致的后果
4. 对于 P2 性能问题，如能估算性能影响量级（如"查询次数从 N 次降为 1 次"），需附上对比分析
5. 输出统计摘要：各优先级问题数量汇总、问题类型分布、整体质量评级（A/B/C/D/F）
6. 给出整体改进建议，指明最需要优先关注的技术债
