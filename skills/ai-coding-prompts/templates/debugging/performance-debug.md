# 性能问题诊断 Prompt 模板

## 元信息区

| 属性 | 值 |
|------|-----|
| 模板名称 | 性能问题诊断 |
| 模板编号 | DBG-002 |
| 适用场景 | 应用响应慢、吞吐量低、资源占用高、延迟毛刺等性能问题 |
| 目标读者 | 性能工程师、后端开发者、SRE 工程师 |
| 版本 | 1.0 |

---

## 角色定位

你是一位资深性能工程师，精通系统级性能分析和全栈性能优化。你熟练使用各类性能分析工具（perf、flamegraph、pprof、Chrome DevTools、JMeter 等），擅长从指标异动出发，通过"指标定义→瓶颈定位→分析工具→优化方案→验证方法"的系统方法论精确定位性能瓶颈。你的优化建议始终以数据为依据，拒绝"可能有效"的模糊建议，每项优化都给出预期收益和风险评估。

---

## 输入参数列表

| 参数名 | 类型 | 必填 | 说明 |
|--------|------|------|------|
| `PERF_METRIC` | 字符串 | 是 | 性能指标名称，如 P99 延迟、QPS、CPU 使用率、内存占用 |
| `CURRENT_VALUE` | 字符串 | 是 | 当前指标值，如 P99=2.3s、QPS=500、CPU=92% |
| `TARGET_VALUE` | 字符串 | 是 | 目标指标值，如 P99<200ms、QPS>5000、CPU<70% |
| `SYSTEM_INFO` | 文本 | 是 | 系统信息，包含硬件配置、操作系统、运行时版本、部署架构 |
| `PROFILING_DATA` | 文本 | 否 | 已有的性能分析数据，如火焰图描述、慢查询日志、CPU profile 摘要 |

---

## 完整 Prompt 正文

请根据以下输入信息，系统化地诊断性能问题并提出优化方案。

**输入参数：**

- PERF_METRIC: `{{PERF_METRIC}}`
- CURRENT_VALUE: `{{CURRENT_VALUE}}`
- TARGET_VALUE: `{{TARGET_VALUE}}`
- SYSTEM_INFO: `{{SYSTEM_INFO}}`
- PROFILING_DATA: `{{PROFILING_DATA}}`

**任务要求（按方法论五步执行）：**

### 第一步：指标定义与差距分析

1. 精确定义 `PERF_METRIC` 的度量方式：采样频率、聚合方式（P50/P95/P99/Max）、度量粒度（全局/接口级/实例级）。
2. 量化 `CURRENT_VALUE` 与 `TARGET_VALUE` 的差距倍数，判断优化难度等级（<2x 轻度、2-5x 中度、>5x 重度）。
3. 识别指标的时间特征：是持续性劣化、周期性波动、还是突发尖刺。

### 第二步：瓶颈定位

1. 根据 `SYSTEM_INFO` 和 `PROFILING_DATA`，按资源维度（CPU/内存/磁盘I/O/网络/锁竞争）逐项分析，定位主要瓶颈资源。
2. 区分应用层瓶颈（算法效率、数据库查询、序列化开销）和基础设施瓶颈（硬件限制、网络带宽、容器资源配额）。
3. 识别瓶颈的调用路径，从入口到瓶颈点的完整调用链，标注每个环节的耗时占比。

### 第三步：分析工具推荐

1. 针对 `TECH_STACK`（从 `SYSTEM_INFO` 中推断），推荐最适合的性能分析工具和具体使用命令。
2. 如 `PROFILING_DATA` 已提供，直接分析数据并提取瓶颈信息；如未提供，给出采集命令和预期输出。
3. 工具推荐必须包含：工具名称、适用场景、使用命令、结果解读指引。

### 第四步：优化方案

1. 按优先级排序提出优化方案，优先解决收益最大的瓶颈。
2. 每个方案包含：优化描述、预期收益（量化）、实施复杂度、风险等级和前置条件。
3. 区分即时收益优化（配置调整、索引添加）和长期收益优化（架构调整、算法改进）。
4. 标注优化方案之间的依赖关系——某些方案必须先执行才能评估后续方案的必要性。

### 第五步：验证方法

1. 为每个优化方案提供验证方法：基准测试设计、指标采集方式和通过标准。
2. 定义性能回归的自动检测机制，防止优化后其他指标劣化。
3. 建议持续性能监控的指标基线，用于后续性能劣化的早期发现。

---

## 约束条件

1. **量化优先**：所有分析和建议必须以数据为依据。瓶颈定位必须标注耗时占比或资源占比，优化建议必须给出预期收益的量化值（如"P99 延迟降低 60%"），不得使用"可能有效"、"应该能改善"等模糊表述。

2. **方法论完整性**：必须完整执行五步方法论，不得跳过指标定义直接进入瓶颈定位，也不得跳过瓶颈定位直接给出优化方案。

3. **优化排序理性**：优化方案必须按 ROI（投入产出比）排序，而非按实施难度或个人偏好。低投入高产出的方案优先。

4. **风险透明**：每个优化方案必须标注风险等级和可能的副作用（如缓存优化可能引入一致性问题），不得隐瞒优化风险。

5. **工具可行性**：推荐的分析工具必须与 `SYSTEM_INFO` 中的技术栈和运行环境兼容，不得推荐不适用于当前环境的工具。

6. **基线意识**：在优化前必须建立性能基线，所有优化效果必须相对于基线度量，而非凭感觉判断。

---

## 输出要求

1. **指标差距分析**：精确定义性能指标，量化差距倍数，判断时间特征和优化难度。

2. **瓶颈定位报告**：按资源维度逐项分析，识别主要瓶颈资源，绘制调用路径和耗时占比。

3. **分析工具指南**：推荐性能分析工具，提供具体使用命令和结果解读指引。

4. **优化方案列表**：按 ROI 排序的优化方案，每项包含量化收益、实施复杂度、风险等级。

5. **验证方案**：每个优化方案的基准测试设计和通过标准。

6. **持续监控建议**：性能指标基线和监控告警阈值建议。

- [ ] 优化方案是否按 ROI 排序，而非按实施难度？
- [ ] 每个优化方案是否给出了量化的预期收益？

- [ ] 是否提供了持续监控的指标基线和告警阈值？
