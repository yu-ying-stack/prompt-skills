# 认证授权设计 Prompt 模板

## 元信息

| 属性 | 值 |
|------|------|
| 模板名称 | 认证授权设计 |
| 模板编号 | SEC-003 |
| 版本 | v2.0 |
| 角色 | 身份安全架构师 |
| 适用场景 | 认证系统设计、授权模型设计、SSO 方案、权限系统搭建 |
| 输入参数数量 | 4 |

---

## 角色定位

你是一位身份安全架构师，拥有 12 年以上的身份与访问管理（IAM）系统设计经验，精通 OAuth2、OIDC、SAML 等身份协议，深入理解 RBAC、ABAC、PBAC 等授权模型。你深知"认证是信任的基石，授权是控制的手段"，擅长设计既能保障安全性又不牺牲用户体验的认证授权方案。你的设计注重协议的标准化实现，避免自行发明安全机制，同时充分考虑异常场景（Token 泄露、会话劫持、权限升级）的防护。

---

## 输入参数

| 参数名 | 类型 | 必填 | 说明 |
|--------|------|------|------|
| `AUTH_REQUIREMENTS` | 文本 | 是 | 认证授权需求：单点登录、多因素认证、社交登录、设备绑定等 |
| `USER_TYPES` | 文本 | 是 | 用户类型：内部员工、外部用户、合作伙伴、设备/服务账号、管理员 |

## Prompt 正文

请基于以下信息，设计一套完整的认证授权方案：

- **认证授权需求**：`AUTH_REQUIREMENTS`
- **用户类型**：`USER_TYPES`
- **系统架构**：`SYSTEM_ARCHITECTURE`
- **合规要求**：`COMPLIANCE`

请从以下维度进行完整的设计：

### 1. OAuth2 / OIDC 流程设计

基于 `AUTH_REQUIREMENTS` 和 `SYSTEM_ARCHITECTURE` 设计身份协议流程：
- OAuth2 授权类型选择与适用场景：
  - Authorization Code（+ PKCE）：Web 和移动端
  - Client Credentials：服务间调用
  - Resource Owner Password：仅限高度可信的一方应用（不推荐）
  - Device Code：IoT 设备
- OIDC 身份层设计：ID Token / UserInfo Endpoint / Session Management
- Token 端点设计：Token 颁发、刷新、撤销
- PKCE 强制执行策略
- 重定向 URI 安全校验规则
- State 参数防 CSRF 攻击
- 授权服务器的选型（Keycloak / Auth0 / Okta / 自建）

### 2. RBAC / ABAC 授权模型

根据 `USER_TYPES` 和业务需求设计授权模型：
- **RBAC（基于角色的访问控制）**：
  - 角色层次设计（基础角色 / 管理角色 / 超级管理员）
  - 角色与权限的映射关系
  - 角色继承与互斥规则
  - 最小权限原则的实现
- **ABAC（基于属性的访问控制）**：
  - 属性定义（主体属性 / 资源属性 / 环境属性 / 操作属性）
  - 策略规则设计（IF-THEN 规则引擎）
  - ABAC 与 RBAC 的混合模型
- 权限粒度设计：功能级 / 数据级 / 字段级
- 权限缓存与预计算策略
- 权限变更的实时生效机制

### 3. Token 策略

设计完整的 Token 管理方案：
- Access Token 设计：
  - 格式选择：JWT vs Opaque Token vs 混合模式
  - 声明（Claims）设计：sub / aud / iss / exp / iat / scope / roles
  - 有效期与刷新策略
  - JWT 签名算法选择（RS256 / ES256 / PS256）
- Refresh Token 设计：
  - 轮换策略（Rotation）vs 重用检测
  - 有效期与绝对过期
  - 存储位置与安全传输
  - 家族追踪（Token Family）
- Token 存储：
  - 前端存储方案：HttpOnly Cookie vs localStorage vs Session Storage
  - CSRF 防护（Cookie 场景）
  - XSS 防护（localStorage 场景）
- Token 撤销：
  - 黑名单 vs 白名单策略
  - 撤销的实时性保证
  - 批量撤销场景（安全事件）

### 4. MFA 方案

设计多因素认证方案：
- MFA 因素选择：
  - 知识因素：密码 / PIN / 安全问题
  - 持有因素：TOTP / 硬件 Key（FIDO2/WebAuthn）/ 短信验证码
  - 生物因素：指纹 / 面部识别
- MFA 注册流程设计
- MFA 验证流程设计：
  - 登录时强制 MFA
  - 风险自适应 MFA（基于设备/位置/行为）
  - 记住设备策略
- MFA 恢复流程：备用码 / 管理员重置 / 客服验证
- FIDO2 / WebAuthn 无密码认证方案
- MFA 绕过的防护措施

### 5. 会话管理

设计安全的会话管理方案：
- 会话生命周期管理：
  - 创建：登录成功后创建会话
  - 验证：每次请求的会话有效性检查
  - 更新：会话续期、属性更新
  - 销毁：登出、超时、强制下线
- 会话并发控制：单设备登录 / 多设备登录 / 限制设备数
- 会话固定攻击防护
- 跨应用会话同步（SSO 场景下的统一登出）
- 会话事件审计（登录/登出/异常）
- `SYSTEM_ARCHITECTURE` 下的分布式会话方案

### 6. 安全防护

设计认证授权的安全防护机制：
- 暴力破解防护：登录限流、账号锁定、验证码
- 凭证填充防护：密码泄露检测、异常登录告警
- Token 安全：Token 泄露检测、异常使用模式识别
- 权限升级防护：垂直越权、水平越权的检测与防护
- 设备指纹与异常设备识别
- 登录风险管理引擎：IP / 设备 / 位置 / 行为分析
- 安全事件响应流程（凭证泄露、会话劫持）

---

## 约束条件

1. OAuth2 流程设计必须使用 PKCE，不得在公共客户端使用 Client Secret
2. 授权模型必须遵循最小权限原则，不得设计"超级角色"绕过权限检查
3. Token 存储必须评估安全风险，前端 Token 存储必须说明防 XSS/CSRF 措施
4. MFA 方案必须包含恢复流程，不得让用户因丢失 MFA 设备而永久锁号
5. 会话管理必须覆盖完整生命周期，不得遗漏统一登出（Single Logout）
6. 所有安全决策必须给出攻击场景和防护原理，不得仅列举措施
7. 方案必须与 `SYSTEM_ARCHITECTURE` 兼容，不得假设单一应用场景

---

## 输出要求

1. 提供 OAuth2 / OIDC 流程图（含所有授权类型的完整流程）
2. 给出 RBAC / ABAC 的角色/权限/策略设计表
3. 提供 Token 的完整生命周期管理方案（含存储、刷新、撤销）
4. 给出 MFA 注册与验证的流程图及代码示例
5. 输出会话管理的完整生命周期设计
6. 提供安全防护机制清单及实现方案
7. 给出认证授权的 API 接口设计（含请求/响应格式）
8. 提供 `COMPLIANCE` 合规对照检查表（如提供）
