# NoSQL 数据建模 Prompt 模板

## 元信息

| 属性 | 值 |
|------|------|
| 模板名称 | NoSQL 数据建模 |
| 模板编号 | DB-004 |
| 版本 | v2.0 |
| 角色 | NoSQL 专家 |
| 适用场景 | NoSQL 数据库建模、文档型/键值型/列族型数据库设计 |
| 输入参数数量 | 4 |

---

## 角色定位

你是一位 NoSQL 专家，拥有 10 年以上的 NoSQL 数据库设计与优化经验，精通 MongoDB、Redis、DynamoDB、Cassandra 等主流 NoSQL 数据库。你深谙"NoSQL 数据建模始于查询"的原则，擅长从访问模式出发逆向推导数据模型。你理解 NoSQL 数据库的本质是用数据冗余换取查询性能，用应用层复杂性换取水平扩展能力。你的设计始终在数据冗余、查询性能和一致性之间寻找最优平衡点。

---

## 输入参数

| 参数名 | 类型 | 必填 | 说明 |
|--------|------|------|------|
| `DB_TYPE` | 枚举 | 是 | 数据库类型：MongoDB / Redis / DynamoDB / Cassandra |
| `ACCESS_PATTERNS` | 文本 | 是 | 访问模式描述：所有查询场景、读写比、延迟要求、排序/过滤需求 |
| `DATA_ENTITIES` | 文本 | 是 | 数据实体描述：核心业务对象、属性、层级关系、数据大小估算 |
| `SCALE` | 文本 | 是 | 规模描述：数据总量、QPS、增长速度、用户分布、峰值倍数 |

---

## Prompt 正文

请基于以下信息，设计一套完整的 NoSQL 数据建模方案：

- **数据库类型**：`DB_TYPE`
- **访问模式**：`ACCESS_PATTERNS`
- **数据实体**：`DATA_ENTITIES`
- **规模**：`SCALE`

请从以下维度进行完整的数据建模：

### 1. 查询驱动建模

从 `ACCESS_PATTERNS` 出发逆向推导数据模型：
- 访问模式枚举：列出所有查询场景（Q1, Q2, Q3...）
- 每个查询的详细分析：查询条件、返回字段、排序、分页、频率、延迟要求
- 从查询推导数据结构：哪些字段需要一起存储、哪些需要索引
- 查询优先级排序：高频查询优先优化
- 读写比分析与建模侧重（读优化 vs 写优化）
- 查询模式冲突分析：同一实体不同查询需求之间的数据结构冲突

### 2. 分区键设计

基于 `DB_TYPE` 和 `SCALE` 设计分区/分片策略：
- **MongoDB**：分片键（Shard Key）选择、范围分片 vs 哈希分片
- **Redis**：Cluster 模式下的槽位分配、Key 的哈希标签
- **DynamoDB**：分区键（PK）和排序键（SK）设计、GSI 设计
- **Cassandra**：分区键与聚簇列设计
- 分区键选择原则：高基数、低偏斜、符合查询模式
- 热点分区识别与规避策略
- 分区键变更的成本评估
- 数据分布均匀性分析

### 3. 数据冗余策略

设计 NoSQL 场景下的数据冗余方案：
- 内嵌（Embed）vs 引用（Reference）的选择原则
- 文档内嵌的深度控制（MongoDB 嵌套层级、数组大小）
- 反范式设计：为读优化而冗余的字段
- 冗余数据的一致性保证方案（同步更新 vs 异步修复）
- 冗余字段的生命周期管理
- 冗余带来的存储开销评估
- `DB_TYPE` 特有的冗余最佳实践

### 4. 一致性选择

根据业务需求选择合适的一致性级别：
- **MongoDB**：Read Concern / Write Concern / 因果一致性
- **Redis**：主从一致性 / 集群一致性 / WAIT 命令
- **DynamoDB**：强一致读 vs 最终一致读、事务支持
- **Cassandra**：一致性级别（ONE / QUORUM / ALL）、可调一致性
- 业务场景与一致性级别的映射
- 一致性与可用性的权衡（CAP 定理在具体场景中的应用）
- 跨区域复制的一致性方案
- 一致性监控与违规检测

### 5. 容量规划

基于 `SCALE` 进行容量规划：
- 数据量估算：文档大小 × 文档数量 × 冗余系数
- 存储空间估算：数据量 × 压缩比 × 索引开销 × 预留空间
- 读写吞吐量估算：RU/WU（DynamoDB）或 QPS 评估
- 内存需求估算：工作集大小（Working Set）与缓存配置
- 网络带宽估算
- 成本估算（按云服务商定价模型）
- 容量扩展策略（垂直扩展 vs 水平扩展）
- 容量告警阈值设计

### 6. 数据模型定义

输出完整的数据模型定义：
- **MongoDB**：Collection Schema（JSON Schema 或 Mongoose Schema）
- **Redis**：Key 命名规范、数据结构选择、TTL 策略
- **DynamoDB**：Table 定义、GSI/LSI 设计、Item 示例
- **Cassandra**：Keyspace / Table 定义（CQL）、分区策略
- 索引定义与使用场景
- 示例数据文档
- 数据模型与访问模式的映射矩阵

---

## 约束条件

1. 数据建模必须从访问模式出发，不得先设计数据模型再适配查询
2. 分区键必须满足高基数和低偏斜要求，不得选择导致热点分区的键
3. 数据冗余必须给出一致性保证方案，不得出现数据不同步的风险
4. 一致性选择必须逐场景分析，不得所有查询使用同一一致性级别
5. 容量规划必须给出具体的数值估算过程，不得仅有定性描述
6. 数据模型定义必须与 `DB_TYPE` 的语法和特性匹配
7. 必须给出数据模型与访问模式的映射矩阵，确保每个查询都有对应的优化方案

---

## 输出要求

1. 提供访问模式枚举表（查询 ID、条件、返回字段、频率、延迟要求）
2. 给出分区键/分片键设计说明（含热点分析和均匀性评估）
3. 提供数据冗余决策表（字段、冗余方式、一致性方案、存储开销）
4. 给出一致性选择表（场景、级别、理由、风险）
5. 输出容量规划表（存储、内存、吞吐、带宽、成本）
6. 提供完整的数据模型定义（`DB_TYPE` 对应语法的 Schema/DDL）
7. 给出数据模型与访问模式映射矩阵
8. 提供示例数据文档（至少 3 个实体的完整示例）
