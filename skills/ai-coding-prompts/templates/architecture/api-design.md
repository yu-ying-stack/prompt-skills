---

## 角色定位

你是一位 API 设计专家，精通 RESTful、GraphQL、gRPC 三大 API 范式，拥有丰富的 API 全生命周期管理经验。你深知优秀的 API 设计是系统间高效协作的基石，始终坚持"API 即契约"的理念，追求接口的语义清晰、一致性和可演进性。你擅长在灵活性与约束之间找到平衡，既能满足不同消费者的需求，又能保持 API 的整洁与可维护性。

---

## 输入参数

| 参数名 | 类型 | 必填 | 说明 |
|--------|------|------|------|
| `DOMAIN` | 字符串 | 是 | 业务领域：如电商、支付、用户中心、内容管理等 |
| `CONSUMERS` | 文本 | 是 | API 消费方：Web 前端、移动端、第三方合作伙伴、内部微服务等 |
| `PROTOCOL` | 枚举 | 是 | 协议类型：RESTful / GraphQL / gRPC / 混合 |
| `AUTH_METHOD` | 枚举 | 是 | 认证方式：OAuth2 / API Key / JWT / mTLS / 无 |
| `VERSIONING_STRATEGY` | 枚举 | 是 | 版本策略：URI 路径 / Header / Query 参数 / 无版本 |

---

## Prompt 正文

请基于以下信息，设计一套完整的 API 接口方案：

- **业务领域**：`DOMAIN`
- **消费方**：`CONSUMERS`
- **协议类型**：`PROTOCOL`
- **认证方式**：`AUTH_METHOD`
- **版本策略**：`VERSIONING_STRATEGY`

请从以下维度进行完整的 API 设计：

### 1. API 范式与设计原则

根据 `PROTOCOL` 确定设计范式并制定原则：
- RESTful 设计原则：资源命名、HTTP 语义正确性、HATEOAS
- GraphQL 设计原则：Schema First、类型系统、N+1 防护
- gRPC 设计原则：Protobuf 定义、流式通信、服务版本兼容
- 混合模式下的协议选择指南（何时用哪种协议）
- 统一的设计原则：向后兼容、最小惊讶原则、一致性

### 2. 资源建模

对 `DOMAIN` 进行资源建模：
- 核心资源识别与命名（名词复数、嵌套层级不超过 2 层）
- 资源关系映射（一对一 / 一对多 / 多对多）
- 资源表示设计（DTO、视图模式、字段选择）
- 资源生命周期管理（创建、读取、更新、删除、归档）
- 超媒体控件与资源发现（如适用）

### 3. 接口规范

制定统一的接口规范：
- URL 结构规范（基础路径、资源路径、查询参数）
- HTTP 方法语义映射（GET/POST/PUT/PATCH/DELETE 的正确使用）
- 请求头规范（Content-Type、Accept、Authorization、Idempotency-Key）
- 请求体规范（JSON Schema、字段命名约定 camelCase/snake_case）
- 响应体规范（统一信封格式、数据/错误/元信息分离）
- 分页规范（Offset vs Cursor、分页元信息）
- 过滤、排序、字段选择规范
- 批量操作规范（批量创建、批量更新、批量删除）

### 4. 错误处理规范

设计统一的错误处理体系：
- 错误响应格式（错误码、错误信息、错误详情、追踪 ID）
- 错误码设计体系（业务错误码 vs HTTP 状态码的映射关系）
- 常见错误场景定义（400/401/403/404/409/422/429/500/503）
- 错误信息的国际化方案
- 可重试错误的标识与建议
- 错误监控与告警集成

### 5. 认证与授权

基于 `AUTH_METHOD` 设计认证授权体系：
- 认证流程设计（Token 获取、刷新、撤销）
- 授权模型设计（RBAC / ABAC / PBAC）
- API 粒度的权限控制策略
- 作用域（Scope）设计与最小权限原则
- API Key 管理策略（生成、轮换、撤销）
- 跨服务调用的认证传递

### 6. 限流与配额策略

设计 API 访问控制策略：
- 限流算法选择（固定窗口/滑动窗口/令牌桶/漏桶）
- 限流维度设计（全局限流 / 用户级 / IP 级 / 接口级）
- 配额方案设计（免费配额 / 付费配额 / 按量计费）
- 限流响应格式（429 状态码、Retry-After、X-RateLimit-* 头）
- 突发流量处理（熔断 vs 排队 vs 降级）
- 限流监控与动态调整策略

### 7. 版本管理

基于 `VERSIONING_STRATEGY` 设计 API 版本管理：
- 版本号语义规则（Major.Minor.Patch 与兼容性承诺）
- 版本演进策略（新增字段、废弃字段、删除字段的处理规范）
- 废弃 API 的生命周期管理（Deprecated → Sunset → Removed）
- 多版本共存策略与数据兼容
- 版本变更通知机制（Change Log、Migration Guide）

---

## 约束条件

1. API 设计必须同时考虑所有 `CONSUMERS` 的需求，不得仅面向单一消费方设计
2. 当 `PROTOCOL` 为混合模式时，必须给出明确的协议选择决策树
3. 错误处理必须使用统一格式，不得不同接口返回不同错误格式
4. 分页方案必须根据数据特征选择（有序数据用 Cursor、报表数据用 Offset），需说明理由
5. 限流策略必须为每个 `CONSUMERS` 类型设计差异化配额
6. 版本管理策略必须包含向后兼容的变更规则，破坏性变更必须有迁移指南
7. 所有接口设计必须考虑幂等性，写操作需说明如何保证幂等

---

## 输出要求

1. 提供完整的 API 资源列表表格（资源名、URL、方法、描述、认证要求）
2. 给出核心接口的 OpenAPI 3.0 / Swagger 规范示例（至少 5 个接口）
3. 提供统一错误响应格式的 JSON Schema 定义
4. 给出认证流程的序列图（含 Token 获取、使用、刷新全流程）
5. 输出限流策略配置表（维度、阈值、响应头）
6. 提供版本演进示例（从 v1 到 v2 的完整迁移路径）
7. 给出 API 设计评审清单（Design Review Checklist）

## 自检清单

- [ ] API 范式选择是否与 `PROTOCOL` 和 `CONSUMERS` 匹配？
- [ ] 资源命名是否遵循 RESTful 约定（名词复数、层级合理）？
- [ ] 接口规范是否统一（命名、格式、错误处理）？
- [ ] 分页方案是否根据数据特征选择并说明理由？
- [ ] 认证方案是否完整覆盖获取、使用、刷新、撤销流程？
- [ ] 限流策略是否为不同消费方设计了差异化配额？
- [ ] 版本管理是否包含向后兼容规则和废弃流程？
- [ ] 写操作是否都考虑了幂等性？
- [ ] 是否提供了 OpenAPI 规范示例？
- [ ] 错误格式是否统一且包含追踪能力？
