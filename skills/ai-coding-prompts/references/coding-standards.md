# 通用编码规范与 Prompt 质量标准

## 一、Prompt 模板设计原则

### 1.1 角色锚定原则

- 每个模板必须以明确的专业角色开头
- 角色定义应包含：专业领域、经验年限暗示、核心能力
- 示例："你是一位拥有 10 年经验的高级前端架构师，精通 React 生态..."

### 1.2 上下文完整性原则

- 必须为 AI 提供足够的上下文信息
- 包含：技术栈版本、项目背景、约束条件、代码片段
- 避免模糊指令，优先具体化

### 1.3 输出可验证原则

- 输出结果必须可验证、可测试
- 包含明确的验收标准
- 提供自检清单或测试方法

### 1.4 安全防御原则

- 显式声明禁止项
- 包含安全检查维度
- 不暴露敏感信息

## 二、变量命名规范

### 2.1 格式标准

- 使用双花括号：`VARIABLE_NAME`
- 变量名使用大写英文 + 下划线分隔
- 命名应自解释，无需额外注释

补充约定：

- 在“输入参数”表格、变量清单、约束说明中，可使用 `VARIABLE_NAME` 作为变量名展示形式
- 在“Prompt 正文”、输出模板、可直接复制给 AI 的提示词片段中，统一使用 `{{VARIABLE_NAME}}` 作为占位符形式
- 同一模板中，不得混用多种占位符风格表达同一层级的插值语义

叙述性引用变量名的保留规则：

- 当文本是在解释“如何使用某个输入变量进行分析、约束校验或自检判断”时，保留 `VARIABLE_NAME` 形式
- 当文本是在向 AI 直接注入上下文值、拼装最终 Prompt、展示可复制输入片段时，使用 `{{VARIABLE_NAME}}` 形式
- 典型保留场景：
  - “基于 `SCALE` 进行容量规划”
  - “方案必须与 `TECH_STACK` 兼容”
  - “是否与 `CONSTRAINTS` 匹配”
- 典型替换场景：
  - “**技术栈：** {{TECH_STACK}}”
  - “**部署环境：** {{DEPLOY_ENV}}”
  - 可直接复制给 AI 的最终 Prompt 正文中的变量位

### 2.2 标准变量分类

| 类别 | 变量名 | 说明 |
| ------ | -------- | ------ |
| 技术栈 | `TECH_STACK` | 使用的技术框架 |
| 技术栈 | `LANG` | 编程语言 |
| 技术栈 | `BUILD_TOOL` | 构建工具 |
| 技术栈 | `DB_TYPE` | 数据库类型 |
| 代码 | `CODE_CONTEXT` | 相关代码上下文 |
| 代码 | `CODE_SNIPPET` | 待处理代码片段 |
| 代码 | `API_CODE` | API 相关代码 |
| 代码 | `COMPONENT_CODE` | 组件代码 |
| 需求 | `REQUIREMENT` | 功能需求描述 |
| 需求 | `CONSTRAINTS` | 约束条件 |
| 需求 | `REFACTOR_GOAL` | 重构目标 |
| 需求 | `DESIGN_GOAL` | 设计目标 |
| 环境 | `DEPLOY_ENV` | 部署环境 |
| 环境 | `OS` | 操作系统 |
| 环境 | `RUNTIME` | 运行时环境 |
| 环境 | `BROWSER` | 浏览器环境 |
| 性能 | `PERF_METRIC` | 性能指标 |
| 性能 | `TARGET_VALUE` | 目标值 |
| 性能 | `QPS_TARGET` | QPS 目标 |
| 性能 | `DATA_SCALE` | 数据规模 |
| 其他 | `FILE_PATH` | 文件路径 |
| 其他 | `MODULE_NAME` | 模块名称 |
| 其他 | `COMPLIANCE` | 合规标准 |
| 其他 | `SECURITY_SCOPE` | 安全审计范围 |

### 2.3 自定义变量规则

- 遵循同样的大写 + 下划线格式
- 添加类别前缀便于识别
- 在模板头部注释区列出所有自定义变量

## 三、模板结构规范

### 3.1 标准模板结构

```text
# [模板标题]

## 元信息
- 适用场景：
- 技术栈：
- 难度等级：

## 角色定位
你是一位 [专业角色]，[核心能力描述]。

## 输入参数
- PARAM_1：[参数说明]
- PARAM_2：[参数说明]

## Prompt 正文

[完整的提示词内容，包含所有变量占位符]

## 约束条件
1. [约束1]
2. [约束2]

## 输出要求
1. [输出项1]
2. [输出项2]

## 输出格式
[指定 Markdown/JSON/表格等]

## 自检清单
- [ ] 检查项1
- [ ] 检查项2
```

章节标题统一要求：

- 使用 `## 元信息`，不使用“元信息区”等变体
- 使用 `## 输入参数`，不使用“输入参数列表”等变体
- 使用 `## Prompt 正文`，不使用“完整 Prompt 正文”等变体
- “角色定位 / 约束条件 / 输出要求 / 输出格式 / 自检清单”标题命名保持完全一致

措辞强度统一要求：

- 硬约束统一使用“必须 / 不得 / 禁止”表述
- 偏好与优先级使用“优先 / 建议 / 可选”表述
- 同一列表中，避免把硬约束和建议性表述混在同一层级而不加区分
- 约束条件中优先写可判定、可验证、可审查的句式，避免“尽量”“适当”“酌情”等弱措辞

输出可验证性补充要求：

- 设计类、评审类、治理类模板的输出要求应尽量落到结构化产物，如表格、清单、流程图、配置片段、决策矩阵
- 若模板用于方案设计，优先要求输出“至少一个”可复核工件，如阶段表、风险表、配置示例、验收清单
- 若模板用于审查或评估，优先要求输出问题级别、影响范围、修复建议或通过条件，避免只给抽象判断

### 3.2 质量评分维度

| 维度 | 权重 | 说明 |
| ------ | ------ | ------ |
| 功能正确性 | 30% | 生成的代码/方案是否满足需求 |
| 安全合规 | 25% | 是否存在安全漏洞或合规问题 |
| 代码质量 | 20% | 可读性、可维护性、最佳实践 |
| 完整性 | 15% | 边界处理、错误处理、文档完善度 |
| 性能考量 | 10% | 性能影响评估和优化建议 |
